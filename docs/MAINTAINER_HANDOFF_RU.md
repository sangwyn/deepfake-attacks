# Передача сопровождения: отладка и администрирование кода

Для агента, который **отлаживает и поддерживает** систему. Запуском кампании
занимается другой агент по `docs/OPERATOR_GPT_RU.md` — вы его не подменяете.

Разделение: он **эксплуатирует**, вы **чините**. Он останавливается на
незнакомом симптоме и передаёт вам. Вы разбираетесь, правите, проверяете и
возвращаете ему исправленную систему.

---

## 1. Первое, что нужно понять

Система построена вокруг одного принципа: **языковой модели не доверяют
результат**. Агент готовит эксперимент, но не выносит вердикт.

```
агент пишет код → ставит задание в очередь → выходит
                            ↓
      планировщик берёт GPU → runner считает → верификатор проверяет
                            ↓
        контроллер (обычный код) читает вердикт → passed / failed
```

Отсюда всё остальное. Когда будете что-то чинить, спрашивайте себя: не даёт ли
эта правка агенту способ объявить успех самому.

### Инварианты, которые нельзя ослаблять

Каждый из них может быть «починен» так, что тесты позеленеют, а наука сломается.

1. **`_require_tracked_inputs`** (`attacklab/runner.py`) — конфиг, серверный
   конфиг, манифест и environment lock обязаны быть в Git до старта. Убрать эту
   проверку легко и заманчиво, когда агент забыл `git add`. Не убирать: она
   единственное, что связывает числа с настройками, которыми они получены.
2. **`passed` только от верификатора.** Контроллер отвергает статус, где агент
   заявил `passed` сам. Проверено тестом `test_worker_may_not_claim_passed`.
3. **Агент не выбирает GPU** и не запускает эксперимент. Только `gpuq submit`.
4. **Каталоги прогонов неизменяемы.** Повторный прогон с тем же конфигом обязан
   упасть, а не перезаписать.
5. **L∞-проекция после каждого шага** плюс аудит по перечитанному с диска PNG.
   `constraint_violations` обязан быть 0, иначе результат несравним.
6. **Общий препроцессинг.** Все атаки берут градиент через
   `attacklab/preprocessing.py`. Атака со своей копией препроцессинга
   несравнима с остальными.

## 2. Что выглядит неправильно, но сделано намеренно

Не «чините» это, не прочитав причину.

**`torch.use_deterministic_algorithms(True, warn_only=True)`**
(`attacklab/runner.py`). Строгий режим падает: у backward дифференцируемого
resize нет детерминированной реализации на CUDA, и первый же семпл убивает
прогон. Воспроизводимость **проверена эмпирически**: два одинаковых прогона,
8 из 8 хешей изображений совпали побайтово. Сиды, `cudnn.deterministic` и
`CUBLAS_WORKSPACE_CONFIG` действуют.

**`--allow-shared-gpu` у планировщика.** По умолчанию карта считается пригодной
только без единого чужого процесса. На этой машине все 8 карт постоянно заняты
коллегами — без флага планировщик не возьмёт ни одну и будет молча опрашивать
очередь вечно. Флаг снимает проверку эксклюзивности, но оставляет требование по
свободной памяти с запасом. У NVIDIA нет резервирования: запас снижает
вероятность столкновения, но не устраняет её.

**Последовательный контроллер.** Один агент за раз. Параллельные воркеры
требуют отдельного git worktree на каждого: у всех `edit: allow` на весь
проект, и `git add` из двух процессов конкурирует за `index.lock`. Поднимать
`--max-running` при последовательном контроллере бесполезно — в очереди всегда
одно задание.

**`permission.edit: allow` у attack-worker.** Сузить по путям **невозможно**: в
OpenCode 1.18.26 `permission.edit` принимает только `ask`/`allow`/`deny`
(`types.gen.d.ts:858`). `ask` ломает автоматическую кампанию, `deny` делает
воркера бесполезным. Настоящая изоляция — только на уровне ОС.

**`"invalid": true` в выводе `opencode debug agent`.** Это **не** признак
невалидного конфига. Встроенный инструмент, включённый по умолчанию у всех трёх
агентов, включая read-only reviewer, чьи ограничения при этом видимо
применяются. Проверено.

**Нулевые пороги удержания** в `specs/attacks/*.yaml`. Так пришло от
пользователя. Отбор финалистов при них формален — это известно и записано.

**Форматный конфаунд датасета.** Все real — JPG, все fake — PNG; метка
предсказывается по расширению файла. Пользователь решил зафиксировать и идти
дальше. Влияет на интерпретацию, не на работоспособность.

## 3. Чего в системе нет

Не выдавайте за готовое:

- **NPR и AIDE не подключены.** Веса есть (`/home/aiattacks/detector_weights/`),
  адаптеров нет. NPR — `resnet50(num_classes=1)`, один логит с сигмоидой. AIDE —
  два логита, и **противоположное** соглашение о метках: `if pred > 0.5: return 0`.
  Перепутать значит получить зеркальный ASR, который выглядит правдоподобно и не
  падает с ошибкой.
- **Отложенного набора нет.** Все атаки сравниваются на одних и тех же 100
  изображениях `test_fake.jsonl`, на них же отчитываемся. Спасает то, что
  параметры заранее прописаны в спецификациях и не подбираются по ответам
  детектора.
- **Латентные методы вне досягаемости.** Нет ни `diffusers`, ни весов
  диффузионной модели, а `requirements.lock` проверяется по хешу.
- **14 гипотез пользователя не начаты** (`hypothesis_descriptions`). Четыре
  выполнимы сейчас, четыре требуют трёх-четырёх детекторов, четыре — диффузии.

## 4. История отказов и чему она учит

Пять остановок кампании. **Ни одна не была поломкой системы** — все были
дефектами конфигурации или формулировок. Полезно тем, что показывает класс
ошибок, которые здесь возникают.

| Что сломалось | Причина | Урок |
|---|---|---|
| Первый прогон агента | конфиг не в Git, а коммитить агенту нельзя | контракт требовал невозможного |
| Планировщик не брал карты | нужен `--allow-shared-gpu` | молчаливый отказ хуже громкого |
| tmux умирал за секунду | `tee` писал в несуществующий каталог | сбой в обёртке, а не в программе |
| Все тесты агента падали | голый `python3` вместо `.venv/bin/python` | у агента не было ни одного рабочего способа |
| Агент писал не тот файл | двусмысленная фраза в `attack.md` | 11 задач поняли верно, одна нет — этого достаточно |

Общее: **система ни разу не выдала неверное число и ни разу не пошла дальше
вслепую**. Останавливалось именно то, что должно останавливаться. Если увидите
падение — сначала предположите, что это защита сработала, а не сломалась.

## 5. Как проверять свои изменения

Обязательный минимум перед любым коммитом:

```bash
.venv/bin/python -m pytest tests
```

104 теста. И отдельно — что прямой запуск даёт столько же, потому что на сервере
`pytest` не установлен:

```bash
for f in tests/test_*.py; do PYTHONPATH=. .venv/bin/python "$f" 2>&1 >/dev/null | grep "^Ran"; done
```

Числа обязаны совпасть. Есть guard, который падает, если класс тестов окажется
после блока `if __name__ == "__main__"` — там они молча не выполняются.

Дальше:

```bash
.venv/bin/python -m attacklab.cli validate-specs --config configs/pipeline/server.yaml
.venv/bin/python scripts/run_campaign.py development --dry-run
```

На сервере дополнительно `preflight --config configs/pipeline/server.yaml --deep`.

**Никогда не коммитьте при упавшем тесте.** Я один раз это сделал, потому что
`&&` в команде не связывал проверку с коммитом. Гейтите явно.

## 8. Как работать с оператором

Он приходит к вам, когда встречает симптом, которого нет в его таблице. От вас
нужно:

1. **Воспроизвести и найти причину**, а не предложить обход. Все пять прошлых
   отказов имели точную причину, и в четырёх случаях сообщение об ошибке прямо
   на неё указывало.
2. **Починить источник**, а не симптом. Если агент записал не тот файл — правьте
   формулировку инструкции, а не добавляйте контроллеру запасной путь поиска.
3. **Проверить, что исправление не разъедется** — добавьте тест или guard, если
   ошибка может повториться.
4. **Вернуть оператору точную команду** для продолжения, с ожидаемым коммитом.

Не запускайте кампанию сами и не отменяйте задания в очереди — это его работа.
Читать состояние можно и нужно.
